# ADR 0001: an evidence-first local deployment evaluator

Status: accepted for v0.1, 2026-09-21. Working name: **PrismBench** (name availability is not a release claim).

## Decision and product test

Conditional GO. llama-bench already measures engine throughput and sweeps parameters; llama-autotune already searches deployment configurations. We should use their runtimes and findings, not build another inference engine or claim that tuning is new. See [competitor research](../competitive-landscape.md).

The small useful product is a local CLI which starts an owned llama-server process, checks what actually ran, preserves unsuccessful attempts, and produces comparable deployment evidence. A user supplies a GGUF and explicit configurations; the output answers whether each workload completed, its TTFT/throughput/resource costs, and whether an explicitly configured OOM fallback completed. A successful context is a **tested point**, not a universal maximum. A recommendation only ranks matched measured workloads; no extrapolated TPS or universal best quantization.

## Scope

- Python >=3.10, argparse, JSON config, psutil, JSON Schema. No service, database, frontend, cloud account, model downloader or credential management.
- One real backend: a local upstream llama.cpp server, version/capability checked. Windows is the first real GPU validation target. Linux has CPU CI and an optional local model integration test; WSL uses Linux binaries and paths.
- A synthetic backend for a one-command offline demo and failure-path tests. Its results never enter hardware recommendations.
- Explicit cases: local model path and quantization label, context capacity, exact input token count, output count, GPU layers, K/V cache type. Default sample sweep: 1K, 2K, 4K, 8K, 16K. FP16/BF16 and other quantizations may be supplied as runtime-compatible GGUFs; validated support is only claimed for tested artifacts.
- A fresh server lifetime for each repetition/attempt. Warmup excluded, single sequence, streaming request, cache erased before measured requests; verify effective context and prompt/output/cache counts.
- Preload and loaded-idle device VRAM, sampled lifecycle peak, process-tree RSS, system memory, startup-to-ready time, TTFT to first nonempty content chunk, engine PP and generation throughput, client total latency. Missing telemetry remains null and has a reason.
- Strict result schema, raw events/logs/requests/hashes, JSON + CSV + Markdown, partial output after failures, finite deadlines, cleanup of owned processes only. Confirmed OOM may trigger a finite user-configured fallback sequence, recorded as separate attempts. Other failures do not silently downgrade.
- Deterministic bundled smoke probes plus a user JSON probe suite. Paired score deltas require matching suite, model family and inference settings; no unpaired result is called quantization loss. Perplexity/lm-eval integration deferred.

## Implementation boundary

`config` validates/resolves input. `backends.base` defines start/tokenize/complete/erase/effective/close, implemented by `llama_cpp` and `synthetic`. `hardware` samples and records scope. `runner` owns repetitions, state/failure/fallback, evidence and quality. `report` exports without invoking inference. `cli` connects these modules. Small modules and a registry are enough for future transformers/vLLM/MLX adapters.

Existing `bench/`, scripts, downloads, weights, locks, authorizations, evidence and reports are a separate local laboratory. Preserve them on disk and preserve its README as `README.lab.md`. Exclude them from Git and the wheel. Their historical measurements are not measurements of this package. New public evidence is generated by the new runner with declared environment caveats.

## Release gates

Config/schema and numerical semantics tests first; independently review core and adapter; fake HTTP/process integration tests for stream/timeout/OOM/cache/cleanup; real Qwen3-8B Q4_K_M GPU runs on the available 4070 SUPER; wheel installation in a fresh environment; README commands verified; final independent audit. Real hardware OOM is not deliberately forced on a desktop; deterministic process fixtures verify recovery, and its hardware validation limitation is disclosed.

Remote publication is separate from local readiness. Do not tag a final release or claim GitHub CI passed before remote CI runs.
